## 11-12（周四）读：改写为什么必须流式，流式 JSON 又怎么拆

### 先说结论

改写内容和评分不一样，**必须走流式**。原因不是「炫技」，是量级完全不同：

- 评分：一个对象，约 100 token，非流式 3 秒出，等得起
- 改写：8 段 × （原句 + 建议 + 理由），约 900 token，全部生成要 15-20 秒

15 秒白屏，用户早关了。所以改写走流式，边出边看。

### 但流式带来一个新麻烦

非流式时，拿到的是一整段可以 `JSON.parse` 的字符串。流式时，每来一个分片你手上都是**半截**：

```
[
{"origin":"负责登录页开发","suggestion":"主导登录页重构，把首屏从 2.1s
```

这个东西 `JSON.parse` 永远失败。等到最后一片才解析，等于白流。

### 解法：数花括号，把「已经完整的对象」一个个抠出来

关键判断只有一句：**深度从 0 变正、再变回 0，就是一个完整对象**。

要注意三种情况，否则会数错：

1. 字符串里的 `{` `}`（比如建议句里写「把 {a} 改成 b」）—— 不计入深度
2. 转义引号 `\"` —— 不能当成字符串结束
3. 半截对象 —— 丢弃，等下一片补齐

```ts
// utils/extractObjects.ts（11-16 你亲手写这个文件）
// 从「还没写完的 JSON 数组」里，把已经完整的对象抠出来
export function extractObjects(text: string): any[] {
  const result: any[] = []
  let depth = 0        // 当前在第几层花括号里
  let start = -1       // 这个对象的起始下标
  let inString = false // 是否在引号内部
  let escaped = false  // 上一个字符是不是反斜杠

  for (let i = 0; i < text.length; i++) {
    const ch = text[i]

    // 在字符串里时，只关心「字符串什么时候结束」，花括号一律不算
    if (inString) {
      if (escaped) escaped = false
      else if (ch === '\\') escaped = true
      else if (ch === '"') inString = false
      continue
    }

    if (ch === '"') {
      inString = true
      continue
    }

    if (ch === '{') {
      if (depth === 0) start = i // 新对象开头
      depth++
    } else if (ch === '}') {
      depth--
      if (depth === 0 && start !== -1) {
        try {
          result.push(JSON.parse(text.slice(start, i + 1)))
        } catch {
          // 坏一个跳过，不影响后面
        }
        start = -1
      }
    }
  }
  return result
}
```

用法是在 `onDelta` 里累加字符串，然后**每次重新扫一遍**：

```ts
let raw = ''
await run({ system: REWRITE_SYSTEM, user: buildRewriteUser(resume, job), json: true }, {
  onDelta: (chunk) => {
    raw += chunk
    list.value = extractObjects(raw) // 已经完整的段落立刻上屏
  },
})
```

看着像 O(n²)（每来一片全量重扫），但总长只有一两千字，实测无感。**先让它对，再谈快** —— 这句话面试可以直接说。

### 我用 4 条用例验证过这个算法

半截数组只捞完整对象、字符串里的花括号不会数错、空串返回空数组、逐字增长时已捞出的数量只增不减。都过了。

### 面试口述版（30 秒）

## 11-13（周五）读：RewriteCard 的组件边界

### 这一节只回答一个问题：什么该做成 props，什么该留在组件里

`RewriteItem` 有四个字段：`origin`（原句）、`suggestion`（建议）、`reason`（理由）、`type`（weak / missing / good）。

**props 只传一个对象，不要拆成四个参数。**

```ts
// 对的写法
const props = defineProps<{ item: RewriteItem; index: number }>()

// 别这么写
// defineProps<{ origin: string; suggestion: string; reason: string; type: string }>()
```

理由很实际：以后模型多返回一个「置信度」字段，`item` 写法改一行类型定义就完事；拆散的写法要去改每一处调用、每一个组件、每一条测试。

### 布局：桌面左右，手机上下

```html
<article class="rw">
  <div class="side">
    <span class="label">原句</span>
    <p class="text">{{ item.origin }}</p>
  </div>
  <div class="side">
    <span class="label">建议</span>
    <p class="text">{{ item.suggestion }}</p>
  </div>
  <p class="reason">{{ item.reason }}</p>
</article>
```

```css
.rw { display: grid; grid-template-columns: 1fr 1fr; gap: 12px; }

/* 手机上一栏放不下两列，改成上下堆叠 */
@media (max-width: 640px) {
  .rw { grid-template-columns: 1fr; }
}
```

`grid-template-columns: 1fr 1fr` 就是「两列等宽」。`1fr` 是「占一份剩余空间」。

### type 决定颜色，不决定布局

- `weak`（表达弱，比如「负责了登录页开发」）→ 黄色左边框
- `missing`（缺 JD 关键词）→ 红色左边框
- `good`（写得好，不用改）→ 绿色左边框

用 `:class="'rw rw--' + item.type"` 拼类名，CSS 里写 `.rw--weak { border-left-color: #d97706 }`。不要用 `:style` 写颜色，散在模板里以后没法统一改。

### 一个刻意的取舍（面试要能讲）

**没做字符级 diff。** 就是没用那种「删掉的字标红、加上的字标绿」的效果。

原因是：要做对必须引 diff 库或自己写最长公共子序列，代码量翻三倍，而用户真正要的是「这句话该怎么改成那样」，整句对比已经够了。**砍功能要说得出理由，这才叫取舍；说不出理由的叫偷懒。**

## 11-15（周日）读：空态 / 加载态 / 错误态

### 先说结论

三种状态不是「三个 if 分支」，是回答三个不同的问题：

- 空态：我现在该干什么
- 加载态：系统是不是死了
- 错误态：我还能做什么

这三段文案写得好不好，比多做一个功能更能看出前端功底。面试问「你项目做了什么细节」，这是最容易拿分的一段。

### 空态：别只写「暂无数据」

新用户第一次打开历史页，一条记录都没有。写「暂无数据」等于把他关在死路上——他知道没数据，但不知道下一步。

要写成「一句说明 + 一个动作」：

> 还没有分析记录。粘一份 JD，30 秒出结果。［去分析］

还有个容易漏的点：**空有两种**。

- 真的一条都没有 → 引导去创建
- 有数据，但被筛选条件过滤空了 → 提示「当前筛选无结果，清空筛选」

两种用同一句文案，用户会以为数据丢了。

### 加载态：转圈不如占位

转圈（spinner）只说明「在等」，但页面高度是 0，数据一到整页往下跳一下。

骨架屏（skeleton，就是按真实内容铺的灰块）把高度先占住，数据到了原地替换，页面不动。这个「不动」有名字：CLS（Cumulative Layout Shift，布局偏移），是 Lighthouse 性能评分里的一项。

两个小坑：

- 请求很快（缓存 100ms 就回），loading 闪一下比不显示更难看 → 延迟 200ms 再显示
- 请求很慢（AI 要 3 秒），必须给「正在做什么」的文字，不能只有一个圈

### 错误态：分「能重试」和「不能重试」

最容易被忽略的地方。所有错误都给一个「重试」按钮，等于骗人。

- 网络断、5xx（服务器内部错误）、超时 → 给「重试」
- 401（Key 无效）、400（参数错）→ 重试一百次也一样失败，给「去设置页检查 Key」

给错按钮比不给更让人烦。

### 代码：一个字段管三种状态

不要写 `isLoading` / `isEmpty` / `isError` 三个布尔量（只能取 true / false 的变量）。原因就是今天的八股题。

```vue
<script setup lang="ts">
import { ref } from 'vue'

// 联合类型：这个变量只能是这五个单词之一，拼错 TypeScript 立刻报错
type Status = 'idle' | 'loading' | 'empty' | 'error' | 'success'

const status = ref<Status>('idle')
const errMsg = ref('')

async function load() {
  status.value = 'loading' // 同一时刻只有一个状态，不可能两态并存
  try {
    const list = await fetchHistory()
    status.value = list.length ? 'success' : 'empty'
  } catch (e) {
    // catch 到的可能是任何东西，先判断是不是标准错误对象再取 message
    errMsg.value = e instanceof Error ? e.message : '未知错误'
    status.value = 'error'
  }
}
</script>

<template>
  <div v-if="status === 'loading'" class="skeleton" />
  <EmptyState v-else-if="status === 'empty'" @create="goHome" />
  <ErrorState v-else-if="status === 'error'" :message="errMsg" @retry="load" />
  <HistoryList v-else-if="status === 'success'" :list="history" />
</template>
```

### 面试口述版（30 秒）
