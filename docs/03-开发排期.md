> 前提：每周 **12 小时**（约每天 2h × 6 天）。每天的任务控制在「一次坐下能做完」的量，做不完就砍，不要熬夜补。
> 每天配套 20 分钟八股，不算在 12h 里，单独列在每周末尾。

**时间分配原则**

## W2｜打通 AI 流式（技术核心周）

**本周目标**：能把字一个一个「流」到页面上，并且能中途停、出错不蹦。

| 天 | 时长 | 必做任务 | 验收标准 |
|---|---|---|---|
| D1 | 2.5h | 写 `api/chat.ts`；`vercel dev` 启动；Vercel 配 `DEEPSEEK_API_KEY` | 用 `curl` 能收到 `data:` 流，不是一次性返回 |
| D2 | 2.5h | `useAIStream`（架构文档 §7 代码）；先接一个假接口（本地 echo）验证解析，再接真 AI | 页面能逐字打印中文，**无乱码** |
| D3 | 2h | `stop()` 取消按钮；`AbortError` 静默；401 / 429 / 500 三种状态提示 | 点停止不出现红色报错；断网有可读提示 |
| D4 | 2.5h | `prompts/score.ts` + `safeParseJSON`；评分接口走**非流式** | 输入简历+JD，3-5 秒返回分数对象 |
| D5 | 2h | `ScoreRing`（conic-gradient）+ 分维度进度条 + `KeywordTags` | 分数、维度、关键词都能正确渲染 |
| D6 | 1.5h | 串主链路：输入 → 点击 → 跳 `/result/:id` | 端到端跑通，不用手改代码 |

**D4 的一个架构修正（重要，别照 PRD 原文做）**

PRD §6 写的是「评分和改写都走流式」，实际做会发现：**JSON 流式无法增量解析**，你拿到半截 `{"score": 62, "dimensions": [` 是 parse 不出来的，只能等全部生成完才能用——那流式就没意义了。

所以改成：

```
点击分析
  ├─ 请求 A（非流式）：评分 → token 少（约 100），2-3s 返回 → 立刻渲染分数
  └─ 请求 B（流式）  ：改写建议 → 边生成边显示，用户看着有反馈
```

这样 3 秒出分数，同时改写内容在下面滚动出现，体验最好，代码也最简单。

> 这个「改需求」的过程本身就是面试素材：**「原设计两个流式，实现时发现结构化数据没法增量解析，所以拆成一非流式一流式。」** 说明你会做取舍，不是照抄文档。

**本周配套八股（每天 20 分钟）**
1. SSE / WebSocket / 长轮询 三者区别与适用场景
2. 为什么 SSE 用 `EventSource` 有局限？fetch 怎么手动解析流
3. `fetch` 和 `axios` 的区别
4. `AbortController` 的作用，怎么取消请求
5. **Vue3 响应式原理：Proxy vs `Object.defineProperty`**（这题必考，练到 2 分钟讲完）
6. 为什么 Proxy 能监听数组变化和对象新增属性，Vue2 为什么不能

## 进度落后怎么砍（重要，别硬扛）

按这个顺序砍，**从下往上砍**：

1. 先砍 → 二期功能（雷达图、导出、投递台账）：本来就不做
2. 再砍 → 面试题预测页（W3D2）：2.5h，可以砍掉后补，MVP 仍成立
3. 再砍 → 历史记录（W3D3）：砍掉后数据只在内存，但演示仍可用
4. 绝对不能砍 → **流式解析（W2）**：这是项目唯一的技术壁垒，砍了就变成调 API 的壳子
5. 绝对不能砍 → **关键词抽取（W1D4）**：这是「不盲目用 AI」的判断力证明
6. 绝对不能砍 → **性能优化 + 数据（W4D1）**：简历上最容易出彩的一条

一句话：**宁可少两个功能，也要保住「流式 + 本地抽取 + 性能数字」这三件事。**
