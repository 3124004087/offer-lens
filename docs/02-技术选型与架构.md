# OfferLens 技术选型与架构

---

## 1. 技术栈总表

| 层 | 选型 | 为什么（面试要能说出这一句） |
|---|---|---|
| 框架 | **Vue 3.4 + 组合式 API** | 逻辑按功能聚合，`useAIStream` 这类状态机天然适合组合式 |
| 语言 | **TypeScript**（保守用法） | 只写 interface + props 类型，不做类型体操。见 §3 |
| 构建 | **Vite 5** | 冷启动 < 1s；`import.meta.env` 管环境变量 |
| 路由 | **Vue Router 4** | 5 个页面，`createWebHistory` + 懒加载 |
| 状态 | **Pinia** | 只放跨页面共享的「当前简历 / 当前 JD / 当前分析」，见 §5 |
| 样式 | **原生 CSS + CSS 变量** | 不用 UI 库。面试时「手写样式」比「调 Element Plus」有说服力 |
| 本地存储 | **IndexedDB**（原生封装） | 见 §6，不引 dexie 这类库，20 行够用 |
| 后端 | **Vercel Serverless Function** | 一个文件，保护 API Key，见 §2 |
| AI | **DeepSeek**（OpenAI 兼容协议） | 中文强、便宜（百万 token 几块钱）、支持 SSE 流式 |
| 部署 | **Vercel** | 免费、`git push` 自动部署、自带 `/api` 路由 |

**为什么不用 ECharts / Element Plus / Axios**

- 图表只有环形分数，`conic-gradient` 一行 CSS 搞定，没必要为它引 1MB
- UI 库会遮住你对 CSS 的掌控，且实习面试常问「这个布局你怎么实现的」
- `fetch` 够用；而且流式必须用 fetch（Axios 对 ReadableStream 支持差）

> 这三个「不用」本身就是面试素材：**能说清为什么不用某个库，比用过十个库更强**。

## 2. 为什么需要一层 Node 代理（核心考点）

### 不能前端直连 AI 的三个原因

1. **Key 暴露**：打包后的 JS 里 `apiKey` 明文可读，任何人 F12 就能白嫖你的额度
2. **CORS**：DeepSeek 等厂商不允许浏览器跨域直连
3. **无法兜底**：限流、重试、敏感内容过滤做不了

### 代理层实现（`api/chat.ts`，就这么多）

```ts
// Vercel Serverless Function —— 只做转发，不碰业务
export const config = { runtime: 'edge' }   // Edge Runtime，冷启动更快

export default async function handler(req: Request) {
  if (req.method !== 'POST') return new Response('Method Not Allowed', { status: 405 })

  const { system, user, json } = await req.json()
  if (!user) return new Response('user is required', { status: 400 })

  const upstream = await fetch('https://api.deepseek.com/chat/completions', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${process.env.DEEPSEEK_API_KEY}`,  // 只在服务端可见
    },
    body: JSON.stringify({
      model: 'deepseek-chat',
      stream: true,
      temperature: 0.3,          // 评分/改写要稳，别太发散
      ...(json ? { response_format: { type: 'json_object' } } : {}),
      messages: [
        ...(system ? [{ role: 'system', content: system }] : []),
        { role: 'user', content: user },
      ],
    }),
  })

  if (!upstream.ok) {
    return new Response(JSON.stringify({ error: 'upstream_failed' }), {
      status: upstream.status,
      headers: { 'Content-Type': 'application/json' },
    })
  }

  // 原样把 SSE 流转给浏览器
  return new Response(upstream.body, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      Connection: 'keep-alive',
    },
  })
}
```

**面试会被追问的三个点，先准备好答案**

| 问题 | 答法 |
|---|---|
| 为什么用 Edge Runtime | 冷启动 ~50ms（Node 是 500ms+），代理层没有 Node API 依赖，Edge 够用 |
| 为什么不直接透传整个上游响应 | 上游可能返回 JSON 错误体而非流，直接透传会让前端 `getReader()` 拿到非 SSE 数据，必须先用 `upstream.ok` 判断 |
| 本地开发怎么办 | `vercel dev` 会把 `/api` 一起跑起来，和线上一致；不能只用 `vite dev` |

## 3. TypeScript 使用策略（基础水平也能上）

**原则：只做「描述」，不做「计算」。**

✅ 要写的：
- 所有数据结构 `interface`（见 PRD §7）
- `defineProps<{ title: string }>()`
- `ref<Analysis | null>(null)`
- 函数参数和返回值

❌ 不写的：
- 条件类型、映射类型、`infer`
- 复杂泛型封装
- 声明文件

> 面试被问「TS 用得怎么样」就诚实说：**"我用 TS 主要做数据结构和组件 props 的类型约束，业务里靠它挡掉大量拼写和空值错误；高级类型我还在学，比如工具类型的实现原理。"** 这比吹牛被戳穿强 10 倍。

## 5. 状态管理边界（Pinia 用多少，面试常问）

**只放这三样到 Pinia**：

```ts
// stores/workspace.ts
export const useWorkspaceStore = defineStore('workspace', () => {
  const resumeText = ref('')
  const jobText = ref('')
  const company = ref('')
  const position = ref('')

  const canAnalyze = computed(
    () => resumeText.value.trim().length > 100 && jobText.value.trim().length > 100
  )
  return { resumeText, jobText, company, position, canAnalyze }

```

**不进 Pinia 的**：表单 input 的临时值、折叠面板的展开态、hover 状态、loading 态。

> 一句话原则：**「跨路由要共享的进 store，只在当前组件活的就用 `ref`。」** 全塞 Pinia 是新手最典型的过度设计。

## 6. IndexedDB 封装（20 行，够用）

```ts
// composables/useLocalDB.ts
const DB_NAME = 'offer-lens'
const VERSION = 1

let dbPromise: Promise<IDBDatabase> | null = null

function openDB(): Promise<IDBDatabase> {
  if (dbPromise) return dbPromise
  dbPromise = new Promise((resolve, reject) => {
    const req = indexedDB.open(DB_NAME, VERSION)
    req.onupgradeneeded = () => {
      const db = req.result
      // 三张表，主键都是 id
      if (!db.objectStoreNames.contains('resumes')) db.createObjectStore('resumes', { keyPath: 'id' })
      if (!db.objectStoreNames.contains('jobs')) db.createObjectStore('jobs', { keyPath: 'id' })
      if (!db.objectStoreNames.contains('analyses')) {
        const store = db.createObjectStore('analyses', { keyPath: 'id' })
        store.createIndex('createdAt', 'createdAt')   // 按时间排序靠索引，别全表读再 sort
      }
    }
    req.onsuccess = () => resolve(req.result)
    req.onerror = () => reject(req.error)
  })
  return dbPromise
}

/** 通用写入 */
export async function put<T>(store: string, value: T) {
  const db = await openDB()
  return new Promise<void>((resolve, reject) => {
    const tx = db.transaction(store, 'readwrite')
    tx.objectStore(store).put(value)
    tx.oncomplete = () => resolve()
    tx.onerror = () => reject(tx.error)
  })
}

/** 通用读取 */
export async function getAll<T>(store: string): Promise<T[]> {
  const db = await openDB()
  return new Promise((resolve, reject) => {
    const tx = db.transaction(store, 'readonly')
    const req = tx.objectStore(store).getAll()
    req.onsuccess = () => resolve(req.result as T[])
    req.onerror = () => reject(req.error)
  })
}
```

> 面试点：**「为什么 `dbPromise` 要做单例缓存？」** —— `indexedDB.open` 每次都开新连接，多标签页会触发 `versionchange` 冲突；缓存后只开一次。

## 7. 核心实现一：`useAIStream`（整个项目的技术心脏）

```ts
// composables/useAIStream.ts
import { ref, onScopeDispose } from 'vue'

interface StreamPayload {
  system?: string
  user: string
  json?: boolean
}
interface StreamOptions {
  onDelta?: (chunk: string) => void
  onDone?: (full: string) => void
  onError?: (msg: string) => void
}

export function useAIStream() {
  const text = ref('')
  const loading = ref(false)
  const error = ref<string | null>(null)
  let controller: AbortController | null = null

  async function run(payload: StreamPayload, opts: StreamOptions = {}) {
    if (loading.value) return          // 同一实例只允许一个请求，避免两路 token 混写
    loading.value = true
    text.value = ''
    error.value = null
    controller = new AbortController()

    try {
      const res = await fetch('/api/chat', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(payload),
        signal: controller.signal,
      })
      if (!res.ok || !res.body) throw new Error(`HTTP ${res.status}`)

      const reader = res.body.getReader()
      const decoder = new TextDecoder()
      let buffer = ''                  // ★ 半包缓冲

      while (true) {
        const { done, value } = await reader.read()
        if (done) break
        buffer += decoder.decode(value, { stream: true })

        // SSE 以 \n 分隔；最后一段可能被网络包切断，必须留在 buffer
        const lines = buffer.split('\n')
        buffer = lines.pop() ?? ''

        for (const line of lines) {
          const trimmed = line.trim()
          if (!trimmed.startsWith('data:')) continue
          const data = trimmed.slice(5).trim()
          if (!data || data === '[DONE]') continue
          try {
            const json = JSON.parse(data)
            const delta: string = json.choices?.[0]?.delta?.content ?? ''
            if (delta) {
              text.value += delta
              opts.onDelta?.(delta)
            }
          } catch {
            // 单个分片坏掉不影响后续，静默跳过
          }
        }
      }
      opts.onDone?.(text.value)
    } catch (e: any) {
      if (e?.name === 'AbortError') return   // 用户主动取消，不算错误
      error.value = e?.message ?? '未知错误'
      opts.onError?.(error.value!)
    } finally {
      loading.value = false
      controller = null
    }
  }

  function stop() {
    controller?.abort()
    loading.value = false
  }

  onScopeDispose(stop)   // 组件卸载自动中断，防止回调往已销毁实例写值
  return { text, loading, error, run, stop }
}
```

**这段代码里藏着 4 个面试必考细节，务必能自己讲：**

1. **为什么不用 `EventSource`？** —— 它只支持 GET，没法带 body 传 prompt；所以用 `fetch` + `ReadableStream` 手动解析
2. **半包（buffer）问题**：一个 SSE 事件可能被拆到两个 TCP 包里，不缓冲就会 JSON 解析失败 → 用 `split('\n')` + `pop()` 留尾
3. **`TextDecoder` 为什么要 `{ stream: true }`**：中文字符是 3 字节，可能被切开，不加参数会出乱码 `�`
4. **`AbortError` 必须单独判断**：否则用户点「停止」会看到红色报错

## 8. 核心实现二：流式渲染的性能优化（可量化）

**问题**：`text.value += delta` 每收到一个 token 改一次响应式数据。DeepSeek 每秒能吐 30-60 个 token，叠加 `v-for` 渲染结构化结果，主线程会被大量微任务和重渲染占满，滚动卡顿。

**解法**：用 `requestAnimationFrame` 把更新合并到帧级别——一帧内收到 10 个 token，只渲染 1 次。

```ts
// composables/useRAFBuffer.ts
import { ref, onScopeDispose } from 'vue'

/**
 * 把高频字符串追加合并到每帧一次
 * 用法：push(chunk) 高频调用，value 自动按帧更新
 */
export function useRAFBuffer() {
  const value = ref('')
  let pending = ''
  let rafId = 0

  function flush() {
    rafId = 0
    if (pending) {
      value.value += pending
      pending = ''
    }
  }

  function push(chunk: string) {
    pending += chunk
    if (!rafId) rafId = requestAnimationFrame(flush)  // 一帧内多次 push 只排一次
  }

  function reset() {
    pending = ''
    value.value = ''
    if (rafId) cancelAnimationFrame(rafId)
    rafId = 0
  }

  onScopeDispose(() => {
    if (rafId) cancelAnimationFrame(rafId)
  })

  return { value, push, reset }
}
```

在 `useAIStream` 里把 `text.value += delta` 换成 `buffer.push(delta)` 即可。

> **怎么证明有效（面试必答）**：Chrome DevTools → Performance → 录 10 秒流式过程 → 看 Main 线程长任务数量。优化前约 40-60 个 > 16ms 的任务，优化后降到个位数，帧率从 30fps 稳定到 60fps。**有数字的优化才叫优化**，这一句能直接碾压 90% 的实习生。

## 9. 核心实现三：AI 返回 JSON 的容错解析

模型不听话是常态：会包 ```json、会加「好的，以下是分析结果：」、会少个括号。三层兜底：

```ts
// composables/useJsonParse.ts
export function safeParseJSON<T>(raw: string): T | null {
  if (!raw) return null
  let s = raw.trim()

  // 第一层：去掉 markdown 代码块包裹
  s = s.replace(/^```(?:json)?\s*/i, '').replace(/```\s*$/, '').trim()

  // 第二层：截取第一个 { 或 [ 到最后一个 } 或 ]
  const start = s.search(/[[{]/)
  if (start !== -1) {
    const openChar = s[start]
    const closeChar = openChar === '{' ? '}' : ']'
    const end = s.lastIndexOf(closeChar)
    if (end > start) s = s.slice(start, end + 1)
  }

  // 第三层：尝试解析，失败返回 null 由调用方降级
  try {
    return JSON.parse(s) as T
  } catch {
    return null
  }
}
```

调用方拿到 `null` 时降级为纯文本展示 + 一句「解析失败，以下是原始输出」，**永不白屏**。

## 10. 核心实现四：关键词抽取（本地，不走 AI）

```ts
// composables/useKeywordExtract.ts

// 词典：注意按「长度倒序」不会自动生效，匹配前统一排序，保证 Vue3 先于 Vue
const SKILLS = [
  'TypeScript', 'JavaScript', 'Pinia', 'Webpack', 'Vite', 'Vue3', 'Vue2', 'Vue',
  'React', 'Node.js', 'ECharts', 'Sass', 'Less', 'Git', 'HTTP', '小程序',
  '性能优化', '工程化', '组件库', '单元测试',
]

/** 是否字母/数字（用来判词边界，避免 Git 命中 Digital） */
const isWordChar = (c: string | undefined) => !!c && /[a-zA-Z0-9]/.test(c)

export function extractKeywords(text: string): string[] {
  const lower = text.toLowerCase()
  // 被占用的区间，防止 "JavaScript" 同一段又被 "Java" 命中
  const used = new Array(lower.length).fill(false)
  const hits = new Set<string>()

  // 长词优先
  const dict = [...SKILLS].sort((a, b) => b.length - a.length)

  for (const word of dict) {
    const target = word.toLowerCase()
    let from = 0
    while (true) {
      const idx = lower.indexOf(target, from)
      if (idx === -1) break
      const end = idx + target.length

      // 区间未被占用
      let free = true
      for (let i = idx; i < end; i++) if (used[i]) { free = false; break }

      // 词边界：左右不能紧跟字母/数字
      const boundaryOk = !isWordChar(lower[idx - 1]) && !isWordChar(lower[end])

      if (free && boundaryOk) {
        hits.add(word)
        for (let i = idx; i < end; i++) used[i] = true
      }
      from = end
    }
  }
  return [...hits]
}
```

**为什么不用分词库**（面试会问）：技能名是专有名词，jieba 这类通用分词会把「Vue3」切成「Vue」+「3」；而且包体积好几 MB。**领域明确的场景，词典匹配 > 通用分词**。

## 11. 关键渲染决策

| 场景 | 决策 |
|---|---|
| 分数环形图 | `conic-gradient` + `@property` 动画，0 依赖 |
| 流式文本光标 | 伪元素 `::after` 闪烁，不额外挂 DOM |
| 长篇改写列表 | 默认只渲染前 5 条 + 「展开全部」，不做虚拟列表（数据量不够大，上虚拟列表属过度设计） |
| 大文本 diff | 不做字符级 diff（O(n·m) 会卡），只做**段落级**对齐，够用且快 |
| 路由 | `component: () => import(...)` 全部懒加载，首屏只加载工作台 |

> "为什么不做虚拟列表" —— 因为改写结果最多 10 段。为 10 条数据上虚拟列表是炫技，反而增加复杂度。**能说出"这里不需要优化"，比乱优化更成熟。**
