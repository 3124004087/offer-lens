## 1. 历史记录永远是空的（DataCloneError）

**发生时间**：2026-11-18（W3D3，IndexedDB 落库当天）

### 现象

分析完跳结果页，一切正常：分数、维度条、关键词全都在。
但点「历史记录」，永远是「还没有分析记录」。

控制台一行黄色警告：

```
[analysis] 本地保存失败，本次结果只在内存里
DataCloneError: Failed to execute 'put' on 'IDBObjectStore':
#<Object> could not be cloned.
```

### 原因

存进 IndexedDB 的对象里，`result` 是从 `useScore` 的 `ref` 里取出来的 **Proxy（代理对象）**。
IndexedDB 写盘前要做「结构化克隆」（structured clone，把对象拆成二进制），
它只认普通对象和数组，**碰到 Proxy 直接抛错**。

```js
const result = ref({ score: 72 })
result.value          // 代理对象，不是普通对象
store.put(result.value)   // ← 报错在这
```

为什么页面上看不出来：`saveScore` 里写库失败被 `catch` 住了，只 `console.warn` 就继续跳转。
而结果页的 `restore()` **先看内存里的 `current`**，内存里明明有，所以压根没读库 ——
一个被吞掉的错误，掩盖了一个 100% 必现的 bug。

### 修法

写库前统一剥成纯数据（`src/composables/useLocalDB.ts` 的 `toPlain`）：

```ts
function toPlain<T>(value: T): T {
  return JSON.parse(JSON.stringify(value)) as T
}

export async function putAnalysis(item: SavedAnalysis): Promise<void> {
  await withStore('readwrite', (store) => store.put(toPlain(item)))
}
```

放在 `putAnalysis` 这一层而不是每个调用方各自处理：调用方经常随手传页面里的响应式对象，
指望每个人记得转换，早晚会漏。

为什么不用 Vue 的 `toRaw`：它只剥最外面一层，`result.dimensions` 这种嵌套里还可能是代理。
JSON 一趟到底，而且「能进 IndexedDB 的数据」本来就该是 JSON 那几种形状。

### 测试怎么写才有用

新用例传一个 `reactive()` 包过的对象。关键动作：**把修复临时撤掉跑一遍**，
确认它报出和线上一模一样的 `DataCloneError`，再放回去变绿。
只写测试不验证「它能不能失败」，等于写了条永远绿的假测试。

### 面试口述版（30 秒）

> 我用 IndexedDB 存分析记录，结果页一直正常，但历史页永远是空的。
> 看控制台发现 `DataCloneError` —— 我把 Vue 的响应式对象直接 `put` 进去了，
> 响应式对象是 Proxy，而 IndexedDB 的结构化克隆不支持 Proxy。
> 修法是写库前用 `JSON.parse(JSON.stringify())` 深拷贝成纯数据。
>
> **更值得说的是这个 bug 被我自己的 `catch` 吞了**：写库失败只打了警告、没中断流程，
> 所以界面看起来一切正常，只是历史永远是空的。后来我的原则是：
> 静默失败必须在界面上留下痕迹，否则就是给自己埋雷。

### 追问预案

- **「`toRaw` 和 JSON 拷贝有什么区别？」**
  `toRaw` 只剥一层，嵌套对象、数组元素里还是代理；JSON 深到底。
  代价是 JSON 会丢掉函数、`undefined`、`Date` 会变成字符串 —— 但这几样本就不该往库里存。
- **「为什么不在 `saveScore` 里就处理好？」**
  那样每个写库入口都得记得写一次。放到最底层（`putAnalysis`）是「一处收口」，
  以后新增调用方不会漏。
- **「这种错为什么测试没抓到？」**
  因为之前的测试传的都是字面量普通对象。是测试数据的真实性不够，不是测试写得少。
  补的用例刻意用 `reactive()` 造真实输入。

### 还能顺带讲的两点

- **内存和存储两份数据，谁先被读**：`restore()` 先看内存再看库（快），
  所以「没写进库」这件事被内存挡住了。缓存能加速，也会掩盖写入失败 —— 值得主动提。
- **结构化克隆和 JSON 不是一回事**：前者支持 `Date`、`Map`、循环引用，后者不支持；
  但前者不支持 Proxy。选哪个取决于数据从哪来。

## 2. 删除为什么要按两下（更新策略的取舍）

**发生时间**：2026-11-18（W3D3，历史页删除功能）

### 做法

历史列表每条记录旁有「删除」。点第一下：按钮变红、文案变「确认删除」，**数据不动**；
点第二下才真的删。`confirmId` 这个 ref 记住「哪一行在等确认」，点别的行会自动把上一个恢复。

```ts
async function handleDelete(item: SavedAnalysis) {
  // 第一下：只标记，不动数据
  if (confirmId.value !== item.id) {
    confirmId.value = item.id
    delError.value = ''
    return
  }
  // 第二下：写库，成功了才从列表里剔掉
  const ok = await analysis.remove(item.id)
  if (!ok) {
    delError.value = '删除失败，可能是浏览器不让写本地数据'
    confirmId.value = null
    return
  }
  list.value = list.value.filter((x) => x.id !== item.id)
  confirmId.value = null
}
```

### 两个决定值得讲

**为什么不用 `window.confirm` 弹窗**
弹窗在点完的瞬间弹出来，手指还在「确定」的位置上，很容易顺手点掉。
按钮自己变红变字，第二下的代价是可见的、需要移动手指的，比弹窗更难误触。

**为什么删除不做乐观更新**
同一个页面里「标记已投递」是乐观更新：先改界面，写库失败了再翻回去 —— 因为它错了可以再点一次。
删除错了**撤不回来**，所以顺序反过来：先等写库成功（`remove` 返回 `true`），才改界面。

一句话原则：**能撤销的操作可以乐观，不能撤销的必须悲观。**

### 面试口述版（30 秒）

> 删除我做了两道确认，但不是弹窗 —— 弹窗刚点完就弹，用户容易顺手点掉确定；
> 改成按钮自己在「删除 / 确认删除」之间切换。
> 另外删除和旁边的「标记已投递」更新策略不一样：点赞类的可以先改界面再写库，
> 删除必须写完再改界面，因为删错撤不回来。判断标准就是这条操作能不能撤销。

### 追问预案

- **「两下确认会不会还是误删？」**
  会，但代价低：删一条记录不影响其他数据，而且按钮状态是局部的，不会误触到别的行。
  真要更保险可以加「撤销」提示条（删完 5 秒内可恢复），那是下一步的优化。
- **「`filter` 和 `splice` 有什么区别，为什么用 `filter`？」**
  `splice` 在原地改数组，`filter` 返回新数组。新数组一定会触发 Vue 的更新，
  不用去想「这个变更 Vue 察觉到没有」。
