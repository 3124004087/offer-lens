# OfferLens 需求文档（PRD）

> 简历 × JD 智能匹配助手 —— 一个用 Vue3 做的、自己每天都会用的求职工具
> 版本：v1.0（MVP）｜目标：4 周内可上线、可写进简历、可被面试深挖 20 分钟

---

## 1. 一句话定位

粘贴一份 JD、灌一份简历，**10 秒内告诉你差在哪、怎么改、会被问什么**。

## 2. 为什么做这个（面试必讲，先想清楚）

找实习时最耗时的不是投递，是**对着 JD 反复改简历**：

- JD 里写的「熟悉 Webpack 构建优化」，我简历里只写了「熟悉前端工程化」，到底算不算命中？
- 一晚上改 3 个版本，第二天自己都分不清哪版投的哪家
- 改完不知道面试官会从这段经历里问什么

现有工具（招聘 App 的简历诊断）要么要付费、要么只给一个模糊分数，不告诉你**具体哪句话该怎么改**。

所以做一个自己的：**输入 → 差距清单 → 逐句改写 → 预测面试题**，全链路闭环。

> 面试话术：这个项目的需求不是编的，我自己每周投 10 家，改简历改到崩溃，才把它做出来。所以每个功能我都能说清为什么在。

## 3. 目标用户与主场景

**唯一主用户**：正在投前端实习的计算机专业学生（就是你自己）。

**主场景（必须走通，其他都是锦上添花）**

1. 我从招聘 App 复制一段 JD，从我的简历复制全文
2. 点「开始分析」
3. 看到：匹配度 62 分、命中 7 个关键词、缺 3 个（Webpack / 性能优化 / 单元测试）
4. 看到 3 段被标红的句子 + 建议改法
5. 看到 8 道这家公司可能问的题，其中 2 道我答不上来 → 记下来去补

## 4. 功能范围

### MVP（4 周内必须完成）

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 双栏文本输入 | 左简历、右 JD，支持粘贴、字数统计、本地草稿自动保存 |
| F2 | 本地关键词抽取 | 内置前端技能词典，纯前端算出「命中 / 缺失」，不消耗 AI |
| F3 | 匹配度评分 | AI 给 0-100 分 + 一句话点评 + 分维度（技能 / 经验 / 项目） |
| F4 | 逐段改写建议 | 简历按段落拆，输出「原句 → 建议句 → 理由」 |
| F5 | 面试题预测 | 按 JD 生成 8 题，分「基础 / 项目 / 场景」三类，可展开看思路 |
| F6 | 本地历史记录 | 每次分析存本地，可回看、可标记「已投递」 |
| F7 | 流式输出 | AI 内容逐字出现，支持中途取消 |

### 二期（做完 MVP 有余力再加，别提前做）

- 多份简历版本管理 + 版本间 diff
- 导出 Markdown / PDF
- 关键词覆盖率雷达图
- 投递台账（公司、时间、状态）

### 明确不做（写进 README 的「非目标」，面试加分）

- ❌ 不做账号体系 / 登录（本地存储足够，省掉 2 周）
- ❌ 不做简历 PDF 上传解析（PDF 排版千奇百怪，解析成本 > 收益，让用户粘贴文本）
- ❌ 不做后端数据库（无多端同步需求）
- ❌ 不做 RAG / 向量检索（文本量才几千字，塞进 context 就够，上向量库是过度设计）

> 面试点：**「你为什么不做一个完整后台？」** —— 因为没用户体系就没必要。我评估过，做账号要 2 周，收益是「换个浏览器能看到历史」，不值。这个判断本身就是工程能力。

## 5. 页面结构与路由

```
/                    工作台（双栏输入 + 开始分析）
/result/:id          分析结果（评分 + 关键词 + 改写建议）
/questions/:id       面试题预测
/history             历史记录
/settings            设置（模型、API 说明）
```

**页面元素清单**

**`/` 工作台**
- 顶部：项目名 + 「历史记录」入口
- 左栏 `TextPanel`：简历（标题「我的简历」）
- 右栏 `TextPanel`：JD（标题「目标岗位」，附「公司名 / 岗位名」两个输入框）
- 底部：「开始分析」按钮（两栏都 > 100 字才可点）+ 预计耗时提示
- 右下角：已抽取到的关键词预览（本地算的，随输入实时更新）

**`/result/:id` 结果页**
- 顶部 `ScoreRing`：环形分数 + 一句话点评
- 分维度小进度条：技能匹配 / 经验匹配 / 项目相关
- `KeywordTags`：绿色「已命中」、红色「缺失」，缺失的 hover 出建议
- 下方 `RewriteList`：每段一张卡片，左右对比「原文 / 建议」，底部「为什么这么改」

**`/questions/:id`**
- 按 `基础 / 项目 / 场景` 三个 Tab 分组
- 每张 `QuestionCard`：题干 → 折叠参考答案 → 底部「会 / 不会」自评
- 底部：「已掌握 3/8」进度

**`/history`**
- 卡片列表：公司名、岗位、分数、时间、状态标签
- 空状态文案要写人话：「还没有分析记录，去工作台试试」

## 6. 核心交互流程

**流程一：首次分析（主链路）**

```
输入简历 + JD
  → 点「开始分析」
  → 本地抽取关键词（同步，< 50ms，立刻显示关键词预览）
  → 并发发起 2 个 AI 请求：
       ① 评分请求（非流式，token 少约 100，2-3s 返回）
       ② 改写建议 + 面试题（流式，边生成边显示）
  → 结果存 IndexedDB
  → 跳转 /result/:id
```

> **关键设计（也是踩坑后的修正）**：最初想两个都走流式，实现时发现**结构化 JSON 无法增量解析**——拿到半截 `{"score": 62, "dimensions": [` 根本 parse 不出来，只能等全部生成完，那流式就白流了。
>
> 所以拆成：**评分走非流式**（token 少、响应快，3 秒出分数），**改写走流式**（内容长，边出边看）。用户在 3 秒内看到分数，同时下方改写内容滚动出现，感知上完全不卡。
>
> 这个取舍本身就是面试素材：能说清「我在哪一步改了原方案、为什么改」，比照着文档写完更值钱。

**流程二：中途取消**

请求中点「停止」→ 已生成内容保留并标注「（已中止）」→ 可重新生成。

**流程三：复看历史**

`/history` 点卡片 → 直接读 IndexedDB → 进结果页，**不发任何 AI 请求**（省钱）。

## 7. 数据结构

全部 TypeScript interface，字段尽量平铺，不做嵌套地狱。

```ts
/** 简历 */
export interface Resume {
  id: string
  rawText: string           // 用户粘贴的全文
  wordCount: number
  createdAt: number
}

/** 岗位描述 */
export interface Job {
  id: string
  company: string           // 用户手填，可空
  position: string          // 用户手填，如「前端开发实习生」
  rawText: string
  keywords: string[]        // 本地抽取结果
  createdAt: number
}

/** 一次完整分析 */
export interface Analysis {
  id: string
  resumeId: string
  jobId: string
  score: number                       // 0-100
  dimensions: DimensionScore[]        // 分维度
  summary: string                     // 一句话点评
  matched: string[]                   // 命中关键词
  missing: string[]                   // 缺失关键词
  rewrites: RewriteItem[]             // 逐段改写
  questions: Question[]               // 面试题
  status: 'draft' | 'done'
  applied: boolean                    // 是否已投递
  createdAt: number
}

export interface DimensionScore {
  name: string      // 技能匹配 / 经验匹配 / 项目相关
  score: number     // 0-100
  comment: string
}

export interface RewriteItem {
  id: string
  origin: string    // 简历原句
  suggestion: string// 建议改写
  reason: string    // 为什么这么改（1-2 句）
  type: 'weak' | 'missing' | 'good'   // 弱表达 / 缺关键词 / 写得好
}

export interface Question {
  id: string
  category: 'basic' | 'project' | 'scene'
  question: string
  hint: string      // 答题思路，2-3 条
  difficulty: 1 | 2 | 3
  mastered: boolean // 用户自评
}
```

**存储方案**

- `localStorage`：设置项（模型、用户偏好）
- `IndexedDB`：`resumes` / `jobs` / `analyses` 三张表，通过 `useLocalDB` 封装
- **为什么用 IndexedDB 不用 localStorage**：localStorage 上限 5MB 且同步阻塞主线程，简历+JD+分析结果一次就 50KB，存 100 次就爆；IndexedDB 异步、容量大。这是面试常问的对比点。

## 8. 接口契约

### 8.1 唯一的后端接口：`POST /api/chat`

**设计取舍**：只做一个通用 AI 代理端点，不按业务拆接口。

理由：
- AI 调用的本质都一样（发 prompt → 收 token），差异只在 prompt
- prompt 放前端，后端完全不知道业务，加功能不用改后端
- 代理层只需要 20 行，维护成本接近 0

```ts
// 请求
interface ChatRequest {
  system: string      // 角色设定
  user: string        // 用户输入（简历 / JD 拼装后的文本）
  json?: boolean      // 是否需要结构化 JSON 输出
}

// 响应：SSE 流，OpenAI 兼容格式
// data: {"choices":[{"delta":{"content":"匹配"}}]}
// data: {"choices":[{"delta":{"content":"度"}}]}
// data: [DONE]
```

**错误约定**

| 状态码 | 含义 | 前端处理 |
|---|---|---|
| 401 | Key 无效 | 提示去设置页检查 |
| 429 | 限流 / 额度不足 | 提示稍后重试，保留已输入内容 |
| 500 | 上游异常 | 显示「重试」按钮，不清空状态 |

### 8.2 三种 prompt 的输出约定

**① 评分（非流式 + JSON）**

`stream: false` + `response_format: { type: 'json_object' }`，一次返回完整 JSON，直接解析。token 少所以很快。

```
你是前端面试官。根据简历和 JD，输出 JSON：
{"score":62,"summary":"...","dimensions":[{"name":"技能匹配","score":70,"comment":"..."}]}
只输出 JSON，不要解释。
```

**② 改写（流式 + JSON 数组）**

```
把简历按「工作/项目经历」拆段，逐段评价并改写。输出 JSON 数组：
[{"origin":"...","suggestion":"...","reason":"...","type":"weak"}]
```

**③ 面试题（流式 + JSON 数组）**

```
按 JD 生成 8 道面试题，3 基础 + 3 项目 + 2 场景。输出：
[{"category":"basic","question":"...","hint":"...","difficulty":2}]
```

> **容错要点**：模型会夹带 ```json 代码块、会在 JSON 前后加解释。解析必须做三层兜底：
> 1. 去掉 ```json 包裹
> 2. 截取第一个 `{` 或 `[` 到最后一个 `}` 或 `]`
> 3. 失败则降级为纯文本展示，不白屏

## 9. 关键词抽取策略（不用 AI 的部分）

**为什么要本地算**：AI 抽取关键词要 2-3 秒、要花钱、结果还不稳定（同一个简历两次跑可能抽出不同词）。而前端技能名是**有限且可枚举**的，用词典匹配又快又准。

**实现要点**

```ts
// 词典按长度倒序，保证「Vue3」优先于「Vue」被匹配
const SKILLS = ['TypeScript','JavaScript','Pinia','Webpack','Vite','Vue3','Vue2','Vue','React','Node.js','ECharts','Sass','Git','HTTP','小程序']

// 已匹配的区间要「挖掉」，避免 "JavaScript" 同时命中 "Java"
```

**三个必须处理的坑（面试追问点）**

1. **长短词遮挡**：`JavaScript` 包含 `Java`、`Vue3` 包含 `Vue` → 按长度倒序匹配 + 匹配后标记已占用区间
2. **大小写**：`vue3` / `VUE3` / `Vue 3` 都要命中 → 统一小写 + 忽略空格再匹配
3. **词边界**：`Git` 不该在 `Digital` 里命中 → 用前后字符判断是否字母边界

## 10. 异常与边界

| 场景 | 处理 |
|---|---|
| 简历或 JD < 100 字 | 按钮置灰 + 提示「内容太少，AI 判断会不准」 |
| 简历超长（> 8000 字） | 截断到 8000 字并提示，避免超 context 和烧钱 |
| 未配置 API Key | 引导到设置页，附申请链接和免费额度说明 |
| 流式中断网 | 保留已生成内容 + 显示「连接中断，已保留 N 字」 |
| JSON 解析失败 | 降级纯文本，控制台留原始响应便于排查 |
| 重复点击分析 | 按钮 loading 态 + 同一时间只允许一个请求 |
| 页面刷新丢失进度 | 输入内容每 2 秒防抖写 localStorage |

## 11. 验收标准（做完这些才算完）

- [ ] 新用户从打开到看到结果，**不超过 3 次点击**
- [ ] 输入 500 字简历 + 500 字 JD，首屏分数在 **5 秒内**出现
- [ ] 流式输出期间页面可滚动、可点击，帧率不塌（Performance 面板无 > 50ms 长任务连续出现）
- [ ] 断网、Key 错误、JSON 乱码三种情况都不白屏
- [ ] 刷新页面后历史记录还在
- [ ] 移动端 375px 宽度下双栏自动变单栏，可正常使用
- [ ] 部署到公网，有可访问链接
